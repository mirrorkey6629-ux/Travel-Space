# Тревел-планировщик — верхнеуровневый план проекта

## Цель продукта

Закрытое веб-приложение для совместного планирования путешествий. Владелец создаёт поездку и определяет её маршрут, а приглашённые участники помогают наполнять города местами, ссылками и другой полезной информацией.

## Основной функционал

1. Пользователь может создать поездку.
2. Владелец поездки может сформировать персональную ссылку-приглашение и отправить её другим людям.
3. Все данные поездки и изменения владельца или участников хранятся на сервере. `localStorage` допустим только для временного прототипа и не является источником истины.
4. Участник, присоединившийся по ссылке, может:
   - просматривать поездку;
   - добавлять в города места для посещения;
   - добавлять и редактировать ссылки и доступные ему материалы;
   - редактировать созданный им контент, если более детальные правила не определены отдельно.
5. Приглашённый участник не может менять основной план поездки:
   - список городов;
   - порядок городов;
   - даты поездки;
   - даты прибытия и отъезда по городам.
6. Владелец может делать всё доступное участнику, а также создавать, изменять, удалять и переставлять города и менять все даты поездки.
7. Для мест используется Google Maps:
   - пользователь добавляет название места и ссылку Google Maps;
   - приложение извлекает или запрашивает стабильный идентификатор/координаты места;
   - добавленная точка отображается на карте соответствующего города и дня;
   - точки показываются в сохранённом порядке;
   - при наличии нескольких точек интерфейс может построить между ними маршрут.

## Роли и права

| Возможность | Владелец | Участник |
| --- | --- | --- |
| Просматривать поездку | Да | Да |
| Приглашать по ссылке | Да | Нет по умолчанию |
| Добавлять места и ссылки | Да | Да |
| Редактировать доступный контент города | Да | Да |
| Создавать и удалять города | Да | Нет |
| Менять порядок городов | Да | Нет |
| Менять даты поездки и городов | Да | Нет |
| Управлять участниками | Да | Нет |

Проверка прав должна выполняться на сервере. Скрытие кнопок в интерфейсе является только дополнительной мерой и не заменяет серверную авторизацию.

## Основные сущности

- `User` — пользователь приложения.
- `Trip` — поездка, её название, общие даты и владелец.
- `TripMember` — связь пользователя с поездкой и его роль (`owner` или `member`).
- `Invitation` — приглашение с безопасным токеном, сроком действия и статусом.
- `City` — город, порядок в маршруте, прибытие и отъезд.
- `TripDay` — календарный день поездки, формируемый из общего диапазона дат.
- `Place` — место в городе/дне, название, исходная ссылка Google Maps, Place ID или координаты и позиция в маршруте.
- `Link` — дополнительная ссылка, относящаяся к городу, дню или месту.
- `Document` — метаданные загруженного файла и ссылка на объект в файловом хранилище.
- `Task` — задача, относящаяся к поездке, городу или конкретному дню.

## Серверная архитектура

- Проект состоит из двух отдельных приложений в одном репозитории:
  - SPA-клиент на React, TypeScript и Vite;
  - HTTP API на Node.js, TypeScript и Fastify.
- Next.js не используется. Серверный рендеринг, React Server Components и другие механизмы рендеринга интерфейса на сервере не применяются.
- SPA собирается в статические HTML/CSS/JS-файлы и после загрузки выполняется в браузере пользователя.
- Публичный базовый путь приложения — `/travel`. Все клиентские маршруты, статические ресурсы, ссылки, приглашения и callback URL должны корректно работать с этим префиксом.
- API доступен под `/travel/api`. Клиент не должен хардкодить абсолютный путь `/api`: базовый URL API задаётся централизованно через конфигурацию окружения.
- Для Vite используется `base`, равный базовому пути. Vite подставляет его в HTML, в `url()` внутри CSS и в `import.meta.env.BASE_URL`, но не переписывает пути, которые JavaScript собирает сам, — в них префикс берётся из `import.meta.env.BASE_URL`.
- Отдельного роутера нет: экран выбирается разбором `window.location`, поэтому любая проверка пути обязана учитывать префикс, а не сравнивать с корнем.
- Собранный SPA обслуживает тот же процесс Fastify, что и API: отдельного веб-сервера для статики в проекте нет.
- Клиентское веб-приложение обращается к Fastify API. Прямой доступ клиента к PostgreSQL или файловому хранилищу запрещён.
- PostgreSQL хранит пользователей, поездки, участников, города, даты, места, ссылки, задачи и метаданные документов.
- Файлы хранятся отдельно от базы данных: в S3-совместимом хранилище либо в выделенной директории сервера с резервным копированием.
- Сервер отвечает за авторизацию, проверку ролей, валидацию дат и целостность маршрута.
- Изменения должны содержать автора и время создания/обновления.
- Секреты Google Maps и почтового сервиса не должны попадать в клиентский репозиторий.

## Распределение вычислений

- Всё, что безопасно и практически возможно выполнить в браузере, выполняется на клиенте, чтобы минимизировать нагрузку на VPS.
- На клиенте выполняются построение календарного представления, сортировка, фильтрация, группировка, drag-and-drop, подготовка отображения маршрута, предварительная валидация форм, клиентское кеширование и optimistic updates.
- Сервер не формирует HTML интерфейса и не выполняет вычисления исключительно ради его отображения, если тот же результат можно получить из уже переданных данных в браузере.
- Клиентская валидация служит для удобства, но не является доверенной. Fastify API повторно проверяет права, входные данные и инварианты перед чтением или изменением защищённых данных.
- На сервере обязательно выполняются авторизация, контроль ролей, окончательная валидация, транзакционное изменение данных, разрешение конфликтов, работа с приглашениями, файлами и секретами, аудит и ограничение запросов.
- Вычисления, результат которых влияет на права доступа, безопасность, целостность данных или биллинг внешних API, нельзя доверять клиенту.
- Несекретные операции Google Maps допускается выполнять в браузере с ограниченным браузерным ключом. Секретные ключи и операции, требующие доверенной среды, выполняются через API.

## Развёртывание

- Приложение разворачивается на одном VPS, где одновременно работают и другие приложения.
- Репозиторий собирает один Docker image, обслуживающий и SPA, и API: под `/travel` Fastify отдаёт статику собранного клиента, под `/travel/api` — свои маршруты.
- Образ публикуется в GitHub Container Registry как `ghcr.io/mirrorkey6629-ux/travel-space`. Сборку выполняет GitHub Actions при push в `main` и при теге `v*`; VPS ничего не собирает и только забирает готовый образ.
- Теги образа: `latest` для `main`, `sha-<короткий хеш>` для каждой сборки, `v1.2.3` для релизных тегов. `sha`-теги служат точками отката.
- Dockerfile использует multi-stage build, минимальный runtime-образ, непривилегированного пользователя и не тянет в финальный слой исходники, dev-зависимости и пакеты, нужные только для сборки.
- Базовый путь вшивается в бандл на этапе сборки через build-arg `BASE_PATH` и тем же значением задаётся в рантайме, чтобы клиент и API не разъехались. В готовом образе префикс изменить нельзя, только пересобрав.
- Всю остальную конфигурацию образ принимает через переменные окружения. Секреты, адрес PostgreSQL и настройки конкретного VPS в образ не встраиваются.
- Все зависимости корневого пакета — сборочные и лежат в `devDependencies`: SPA бандлится целиком, поэтому в рантайме нужны только зависимости `apps/api`. Новый клиентский пакет добавляется в `devDependencies` корня, иначе он попадёт в production-образ и раздует его. Runtime-зависимости сервера живут в `apps/api/package.json`.
- Миграции применяет сам контейнер при старте, до открытия порта, под advisory-блокировкой PostgreSQL. Блокировка гарантирует, что при одновременном старте нескольких экземпляров файлы накатит ровно один, а остальные дождутся результата.
- `TRAVEL_SKIP_MIGRATIONS=true` — аварийный выключатель, позволяющий поднять контейнер, не трогая схему.
- Образ предоставляет healthcheck: `GET /travel/api/health` проверяет доступность базы, а `HEALTHCHECK` внутри образа опрашивает его средствами Node, без внешних утилит.
- Репозиторий содержит эталонный Compose-файл приложения. Он служит исполняемой документацией, пригоден для самостоятельного запуска и не содержит реальных секретов, доменов, абсолютных путей VPS и обязательных имён общесерверных сетей.
- Итоговый Compose конкретного VPS хранится отдельно на сервере: там задаются домен, TLS, reverse proxy, сети, volumes, секреты и лимиты ресурсов.
- Общий reverse proxy VPS принимает HTTPS-трафик и направляет `/travel/` в контейнер приложения целиком, включая `/travel/api/`.
- Порты контейнера наружу не публикуются: сервис подключается к внутренней сети reverse proxy.
- Сервер отдаёт `index.html` на все GET-запросы под `/travel/`, не совпавшие ни с файлом, ни с маршрутом API, чтобы прямое открытие и обновление вложенных клиентских URL работали. Запросы под `/travel/api/` в этот fallback не попадают и получают JSON-ошибку.
- Статические ресурсы, manifest, favicon и возможный service worker должны учитывать `/travel`; scope service worker не должен выходить за `/travel/`.
- Cookie авторизации, если применяется cookie-сессия, должна быть `HttpOnly`, `Secure`, иметь подходящий `SameSite` и по возможности ограничиваться `Path=/travel`.
- Внешние URL — ссылки-приглашения, OAuth callback, ссылки из email и Google Maps callbacks — формируются из конфигурируемого публичного origin и base path, а не из захардкоженного домена.
- Reverse proxy отвечает за TLS, ограничения размера запроса и базовую защиту от некорректного или слишком медленного трафика; API дополнительно реализует собственную валидацию и rate limiting.
- Файлы хранятся в volume, подключённом к `/app/data/uploads`. Резервное копирование базы и этого volume выполняется на стороне сервера.

## Публикация изменений

Ветка `main` — это продакшен. Push в неё запускает сборку образа, а сервер
забирает свежий `latest` автоматически, без ручного шага. Непроверенный коммит
в `main` означает лежащий сайт, а не «поправлю следующим коммитом».

- Не пушить в `main` код, который не запускается. Ветка не является черновиком: незавершённая работа живёт в отдельной ветке и приезжает через pull request.
- Перед push убедиться, что проходят `pnpm typecheck`, `pnpm build` и `pnpm build:api`. Ошибка типов ломает сборку образа: сломанный код до сервера не доедет, но и обновление тоже не приедет.
- Перед push убедиться, что приложение стартует с чистой базой: `docker compose up -d --build`, затем открыть `http://127.0.0.1:8080/travel/` и проверить затронутый сценарий.
- Изменение схемы обязано ехать вместе с миграцией в `apps/api/src/migrations`. Контейнер применяет миграции сам при старте, поэтому забытая в коммите миграция уронит новый контейнер в restart-loop.
- Миграция и использующий её код должны быть в одном коммите: между ними нет промежуточного состояния, в котором сервер работал бы корректно.
- Миграции пишутся только вперёд и без потери данных: откатных миграций в проекте нет. Уже применённые файлы нельзя переименовывать и удалять — они записаны в `schema_migrations` по имени, и переименованный файл применится повторно.
- Новая обязательная переменная окружения добавляется либо с безопасным значением по умолчанию, либо одновременно с правкой серверного `.env`. Иначе контейнер не поднимется.
- Smoke-тест в CI (`.github/scripts/smoke-test.sh`) поднимает собранный образ с чистой базой и проверяет health, отдачу статики, fallback клиентских маршрутов и отказ анонимному доступу. Образ не публикуется, если тест не прошёл. При появлении новых критичных путей тест дополняется.
- Откат выполняется на сервере командой `bash travel-update.sh --tag sha-<хеш>`. Закрепление тега заодно останавливает автообновление, пока тег не вернут на `latest`.

## Инварианты данных

- Даты города находятся внутри общего диапазона поездки.
- Дата отъезда не раньше даты прибытия.
- Календарь строится только по датам поездки.
- Только владелец может менять маршрут и даты.
- Участник получает доступ только после принятия действительного приглашения.
- Удаление города не должно молча удалять связанные данные: требуется подтверждение и определённая стратегия удаления/архивации.
- Google Maps URL сохраняется в исходном виде, но для отображения карты по возможности дополнительно сохраняются Place ID и координаты.

## Текущее состояние

React-клиент подключён к Fastify API: регистрация и вход выполняются по email и обязательному паролю, который пользователь всегда задаёт вручную. Подтверждение почты и восстановление пароля пока не входят в проект, доступ к отправке писем не требуется. Поездки, города, места, задачи и метаданные документов хранятся в PostgreSQL. Файлы локально хранятся в `data/uploads`. При первом входе в пустой аккаунт старая поездка однократно импортируется из `localStorage`, после чего `localStorage` больше не является источником данных. До продакшена нужно перенести файлы в S3-совместимое хранилище и добавить обработку конфликтов одновременного редактирования.

Один аккаунт может состоять в нескольких поездках. Создатель поездки получает роль `owner`, приглашённые по ссылке — `member`: участники могут добавлять места, ссылки, задачи и документы, но не менять название, даты и список городов. Владелец может удалять гостей из поездки; гость не может удалить владельца или других участников. Для каждой поездки одновременно действует не более одной ссылки-приглашения; создать или заменить её может только владелец, срок действия задаётся при создании. Удалить поездку может только владелец после точного ручного ввода её названия.

Владелец может экспортировать поездку в переносимый файл `.travelspace` и импортировать его в другой экземпляр приложения. Экспорт включает поездку, города, места, задачи и содержимое документов, но не включает участников и приглашения. Импорт всегда создаёт новую поездку, владельцем которой становится импортирующий пользователь; запись данных и файлов должна быть атомарной с очисткой файлов при ошибке.

## Дизайн-система и правила интерфейса

### Тексты интерфейса

- Если текст интерфейса формулируется самостоятельно, точка ставится только после промежуточных предложений. После последнего предложения точка не ставится.

### Типографика

- Основной шрифт — `Inter` с системными fallback-шрифтами.
- `Head L`: 32px, Medium (`500`).
- `Head M`: 20px, Medium (`500`).
- `Text`: 15px, Regular (`400`).
- `Text S`: 13px, Regular (`400`).
- Начертание Semibold в интерфейсе не используется.
- Группа `Head L + Text` имеет вертикальный отступ 8px.
- Группа `Head M + Text` имеет вертикальный отступ 4px.
- Типографика и типографические группы оформляются общими компонентами или токенами. Локальные размеры и веса допустимы только для нового, отдельно согласованного стиля.

### Кнопки и иконки

- Обычная кнопка — единый компонент с темами:
  - `primary`: белый фон, чёрный текст;
  - `secondary`: полупрозрачный белый фон, белый текст.
- Размеры обычной кнопки:
  - `L`: основной крупный вариант;
  - `M`: высота 48px, текст в стиле `Text`.
- Обычная кнопка может содержать иконку слева от текста. Отступ между иконкой и текстом — 4px; размер иконки — 28px для `L` и 20px для `M`.
- `IconButton` — один компонент, принимающий нужную иконку. Размеры: `L`, `M`, `S`. Темы: `primary`, `secondary`, `transparent`.
- У `transparent`-варианта нет фона в обычном состоянии; при hover фон становится таким же, как у `secondary`.
- Иконка всегда центрируется внутри `IconButton`.
- Для широкой строки добавления используется общий компонент с плюсом на всю доступную ширину, а не отдельная круглая кнопка.
- Отдельный компонент `Danger button` не используется.
- Иконки берутся из общей библиотеки SVG-ассетов, а не вставляются текстовыми символами. Цвет интерфейсных иконок — чистый белый `#FFFFFF`, если для конкретного состояния не задана прозрачность.

### Поля, селекты и информационные строки

- `Input` — единый компонент с темами `default` и `accent`. `accent` используется, в частности, на экранах авторизации и в важных подтверждающих формах.
- У `Input` есть независимые свойства показа подписи и иконки, а также состояния `empty`, `filled`, `disabled` и `focus`.
- Высота поля — 60px, скругление — 16px. Фокус оформляется проектным состоянием без стандартной браузерной обводки.
- Автозаполнение браузера не должно менять фон поля на белый или менять проектный цвет текста.
- `Select` — единый компонент с вариантом содержимого `date` или `list`; для дат используется иконка календаря, для времени суток — иконка времени.
- `InfoRow` объединяет ранее отдельные информационные строки. Он поддерживает:
  - ноль, одну или две кнопки справа;
  - тему кнопок `transparent` или `secondary`;
  - изображение, включаемое отдельным свойством;
  - форму изображения `square` или `circle`.
- Изображение в `InfoRow` имеет размер 54×54px. Квадратный вариант имеет скругление 8px.
- Вертикальные внутренние отступы `InfoRow` — 16px. Без изображения левый отступ текста — 20px.

### Фоны, стекло и компоновка

- Экраны авторизации, регистрации, списка поездок и библиотеки компонентов используют общий космический фон со звёздами.
- Звёзды движутся по направлению к пользователю, без кругового движения и без лучей. При переходах между шагами авторизации фон и логотип не перемонтируются и не сбрасывают анимацию.
- Экраны конкретной поездки используют текущее фоновое изображение осеннего сада.
- Основные панели и вложенные плашки используют эффект стекла с `backdrop-filter`; блюр нельзя убирать при перестройке разметки.
- На десктопе базовый отступ от краёв экрана — 32px, если для конкретного экрана не согласовано иное.
- Левая и правая колонки дешборда прокручиваются независимо, занимают доступную высоту, не обрезают контент и не показывают полосы прокрутки.
- Полноэкранные режимы используют кнопку назад в левом верхнем углу. Крестик применяется для закрытия локального состояния или подтверждения внутри контейнера.
- Добавление и редактирование сущности по возможности происходит заменой содержимого существующей стеклянной панели, а не открытием дополнительного модального окна.
- Анимация смены содержимого может менять прозрачность, но не должна сдвигать интерфейс, если движение отдельно не согласовано.

## Правила отображения дат и длительности

- Календарь содержит только даты, входящие в диапазон поездки.
- В диапазоне одного месяца название месяца не дублируется: `4–6 октября`, `4–15 октября`.
- Длительность отображается полным словом с правильным склонением: `1 день`, `2 дня`, `5 дней`; сокращение `дн` не используется.
- Для прибытия и отъезда хранится период суток: `утро`, `день` или `вечер`.
- Длительность города учитывает периоды суток и может иметь шаг 0,5 дня. Например, прибытие 14-го днём и отъезд 15-го утром дают 0,5 дня.
- Во время путешествия прошедшие дни скрываются из актуального календарного представления.

## Устойчивые правила взаимодействия

- При выборе города его подробности заменяют календарную область в правой колонке; выбранный город помечается `📌` в списке.
- Переезд между соседними городами является одной сущностью. Документ, загруженный для поезда `Осака — Нара`, отображается и как отправление из Осаки, и как прибытие в Нару.
- Если у пользователя одна поездка, она открывается автоматически. При нескольких поездках доступен отдельный экран выбора и создания поездок.
- Ссылка-приглашение для поездки одновременно может быть только одна; новая ссылка отзывает предыдущую.
- Количество участников в заголовке поездки кликабельно только для владельца и открывает экран управления участниками. В обычном состоянии текст сохраняет стандартный цвет, без подчёркивания; при hover становится чисто белым.
- Удаление поездки требует точного ручного ввода её названия.
- Экспорт и импорт поездки доступны только владельцу.

## Транспорт между городами

- Для перемещения поддерживаются типы `поезд`, `самолёт`, `автобус` и `корабль`. Выбор типа оформляется общим переиспользуемым компонентом `Tabs`; выбранный таб не получает hover-состояние.
- Первый транспорт поездки называется `Приезд`, последний — `Отъезд`, а промежуточные переезды называются по паре соседних городов.
- В транспортной форме хранятся тип транспорта, время отправления, время приезда, название вокзала/аэропорта/порта, ссылка Google Maps, заметки и билет.
- Время вводится вручную в формате `ЧЧ:ММ`; браузерный time-picker и встроенная кнопка-часики не используются. Проектная иконка времени располагается в начале поля.
- Галочка готовности транспорта появляется только когда заполнены все поля формы и прикреплён хотя бы один файл билета. Эмодзи типа транспорта в меню и заголовках сохраняются.
- Название и ссылка точки прибытия синхронизируются с местом в городе на дату приезда. Изменение названия или ссылки должно обновлять существующее связанное место, а не создавать дубликат.
- Карточка транспорта редактируется нажатием на саму плашку. Если билет прикреплён, отдельная кнопка документа открывает его напрямую.

## Отели

- Карточка `Твой отель` открывает форму отеля для выбранного города. Заголовок формы имеет вид `Отель <название города>`, центрируется как заголовок транспортной формы и сопровождается пояснением об условиях готовности.
- В форме отеля хранятся время заселения, время выселения, название, ссылка Google Maps, заметки и файл брони.
- Галочка готовности отеля появляется только когда заполнены все поля и прикреплён файл брони отеля.
- Сохранённый отель добавляется как место в первый день города. Изменение названия или ссылки отеля должно синхронно обновлять это место без создания дубликата.
- В карточке отеля снаружи показываются время заселения и название отеля. При наличии брони отдельная кнопка документа открывает файл напрямую.

## Документы билетов и броней

- Прикрепление документов оформляется через общий `InfoRow` с изображением. Пустое состояние целиком кликабельно и открывает выбор файла; изображение в нём показывается с прозрачностью 50%.
- Пустой билет: заголовок `Прикрепить билет`, подзаголовок `Лучше в PDF формате`, справа кнопка с плюсом. Пустая бронь: заголовок `Прикрепить бронь` с тем же подзаголовком и кнопкой.
- Загруженный билет: заголовок `Билет`, подзаголовок — имя файла. Загруженная бронь: заголовок `Бронь отеля`, подзаголовок — имя файла.
- Нажатие на заполненный `InfoRow` открывает документ. Справа размещаются две независимые кнопки: скачать и удалить. Нажатие на них не должно одновременно запускать открытие строки.
- После прикрепления или удаления документа интерфейс обновляется сразу, без закрытия и повторного открытия формы.
- Для документов используются данные фактически загруженных файлов, а не устаревшее строковое имя. После удаления последнего файла строка немедленно возвращается в пустое состояние.

## Google Maps в интерфейсе города

- Нажатие на точку карты заполняет поля названия места и ссылки Google Maps. Сохранённые места выбранного города и дня отображаются маркерами на карте.
- Нажатие на место в боковом списке фокусирует его на встроенной карте приложения и не открывает внешний браузер.
- Ссылка Google Maps сохраняется в исходном виде. Для устойчивого отображения дополнительно сохраняются координаты и, когда доступен, Place ID.
- Клиентский ключ Google Maps задаётся только через `VITE_GOOGLE_MAPS_API_KEY`. Значение ключа не записывается в `AGENTS.md`, исходники или коммиты.
- Браузерный ключ считается публичным идентификатором, но обязательно ограничивается разрешёнными сайтами и только необходимыми API. Серверные секретные ключи никогда не передаются клиенту.
- Скрипт Google Maps загружается один раз и переиспользуется. Карта не должна перемонтироваться или выполнять повторное геокодирование без изменения входных данных; это уменьшает расход квот и стоимость API.

## Библиотека компонентов

- Живая библиотека доступна по клиентскому маршруту `/travel/components` и должна показывать те же общие компоненты, которые используются в приложении, а не отдельные визуальные копии.
- Навигация библиотеки расположена в левой колонке, группы компонентов — в правой прокручиваемой области. Обе области не должны обрезать карточки при прокрутке и не показывают scrollbar.
- Для вариантов компонента используются интерактивные настройки, когда это отражает реальные props: тоглы для независимых boolean-свойств и селекты для взаимоисключающих вариантов.
- При появлении повторяющегося паттерна сначала расширяется общий компонент. Одноразовая копия разметки и CSS допустима только когда паттерн действительно отличается по поведению.

## Согласованные, но отложенные изменения

Следующие решения согласованы, но не считаются реализованными до изменения кода и проверки интерфейса:

- приглашение действует ровно 24 часа;
- текст экрана участников явно сообщает о сроке 24 часа и о том, что новая ссылка отключит предыдущую;
- активная ссылка сразу показывается в `accent`-поле, а основная кнопка называется `Скопировать ссылку`;
- организатор поездки показывается первым в списке участников: имя и email, круглая стандартная аватарка, без кнопки удаления;
- гости идут после организатора и могут быть удалены владельцем.

## Правила ведения проекта

- Этот файл хранит устойчивые продуктовые, архитектурные и визуальные решения, но не пошаговую историю переписки.
- Приоритет источников: последний явный запрос пользователя → `AGENTS.md` → фактическая реализация. Если новый запрос меняет устойчивое правило, после реализации нужно обновить этот документ.
- Перед изменением существующего паттерна следует сначала найти его общий компонент и токены; не создавать локальную вариацию без необходимости.
- После изменений интерфейса нужно проверить целевой сценарий в браузере, включая scroll, clipping, hover, focus, disabled и autofill, если они затронуты.
- Перед публикацией по-прежнему обязательны `pnpm typecheck`, `pnpm build` и `pnpm build:api`, а для серверных изменений — проверка запуска с чистой базой.
- В `.gitignore` добавляются только секреты, локальные данные, зависимости и генерируемые артефакты, которые действительно не должны храниться в Git. Неиспользуемые файлы не скрываются через `.gitignore`: их либо оставляют, либо осознанно удаляют.
