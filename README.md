# Travel Space

React/Vite-клиент и Fastify/PostgreSQL API для совместного планирования поездок.

Приложение публикуется под базовым путём `/travel`, API — под `/travel/api`.
Префикс задаётся переменной `BASE_PATH` и вшивается в клиентский бандл на этапе
сборки, поэтому клиент и сервер всегда используют одно и то же значение.

## Локальный запуск интерфейса

```bash
pnpm install
pnpm dev
```

Интерфейс: `http://127.0.0.1:4173/travel/` или по локальному IP компьютера на
порту `4173`. Открытие корня `/` вернёт 404 — приложение живёт под префиксом.

## Локальный запуск backend

Нужны Node.js, pnpm и Docker Desktop (только для PostgreSQL).

```bash
cp .env.example .env
pnpm install
pnpm db:up
pnpm db:migrate
pnpm dev:api
```

API работает на `http://127.0.0.1:3000/travel/api`. Проверка:

```bash
curl http://127.0.0.1:3000/travel/api/health
```

Vite проксирует `/travel/api` на локальный API, поэтому клиент сможет обращаться к API относительным URL без CORS и без хардкода хоста.

PostgreSQL является источником истины для поездок. После первого входа старая поездка из `localStorage` один раз импортируется в пустой аккаунт, затем локальная копия удаляется. Bearer-токен сессии хранится в браузере.

### Локальная авторизация

1. `POST /travel/api/auth/register` с `email`, `displayName` и вручную заданным `password` создаёт аккаунт и возвращает bearer-токен.
2. `POST /travel/api/auth/login` с `email` и `password` выполняет вход и возвращает bearer-токен.
3. Пароль обязателен, должен содержать не менее 8 символов и хранится только в виде scrypt-хеша с индивидуальной солью.
4. Подтверждение почты и восстановление пароля пока не реализуются; отправка писем приложению не требуется.
5. Защищённые запросы используют `Authorization: Bearer <token>`.

### Что уже поддерживает API

- регистрация и вход по email и паролю, серверные сессии;
- создание и чтение поездок;
- роли владельца и участника;
- несколько поездок в одном аккаунте и автоматическое открытие единственной;
- временные многоразовые приглашения: одна активная ссылка на поездку, создавать и заменять её может только владелец;
- защищённое удаление поездки с ручным вводом её названия;
- города и даты с серверной проверкой границ поездки;
- места Google Maps и задачи;
- загрузка и скачивание документов;
- полный экспорт поездки владельцем в файл `.travelspace` и импорт этого файла в другой экземпляр приложения;
- запрет участникам изменять основной маршрут;
- автор и время создания записей.

Файлы локально сохраняются в `data/uploads`, метаданные — в PostgreSQL. Для production директорию можно заменить S3-совместимым хранилищем без изменения публичного API.

### Перенос поездки между экземплярами

В списке поездок владелец может скачать экспорт через кнопку «Экспорт», а затем загрузить его через «Импорт» на локальном или развёрнутом сайте. Файл `.travelspace` содержит название и даты поездки, города, места, задачи и сами вложенные документы. Участники и ссылки-приглашения не переносятся: импорт создаёт отдельную поездку, владельцем которой становится пользователь, выполнивший импорт.

Импорт выполняется транзакционно: при ошибке поездка не создаётся, а уже записанные на диск файлы удаляются. Максимальный суммарный размер файла импорта задаётся переменной `MAX_IMPORT_BYTES`; ограничение размера одного вложения остаётся `MAX_UPLOAD_BYTES`.

## Запуск целиком в Docker

Поднимает базу и приложение ровно так, как они работают на сервере: один
контейнер отдаёт и собранный SPA, и API, миграции применяются при старте.

```bash
docker compose up -d --build
```

Приложение: `http://127.0.0.1:8080/travel/`.

Это же — обязательная проверка перед push в `main`, см. «Публикация изменений»
в `AGENTS.md`.

## Развёртывание

Образ собирается в GitHub Actions при push в `main` и публикуется как
`ghcr.io/mirrorkey6629-ux/travel-space`. Перед публикацией CI поднимает собранный
образ с чистой базой и прогоняет `.github/scripts/smoke-test.sh`: проверяются
health, отдача статики, fallback клиентских маршрутов и отказ анонимному доступу.
Не прошедший тест образ в registry не попадает.

Теги:

| Тег | Когда появляется | Назначение |
|-----|------------------|------------|
| `latest` | push в `main` | то, что разворачивается на сервере |
| `sha-<хеш>` | каждая сборка | точка отката на конкретный коммит |
| `v1.2.3` | git-тег `v*` | релизная версия |

Сервер забирает готовый образ и ничего не собирает. Конфигурация целиком
приходит через переменные окружения — см. `.env.example`.

### Первая публикация

GHCR создаёт новый пакет приватным, даже когда репозиторий публичный, и
`GITHUB_TOKEN` не имеет права менять видимость. После первой успешной сборки
нужно один раз открыть
[настройки пакета](https://github.com/users/mirrorkey6629-ux/packages/container/travel-space/settings)
и переключить видимость на **Public**. Тогда сервер тянет образ без авторизации.

Если пакет остаётся приватным, на сервере понадобится
`docker login ghcr.io` с токеном, имеющим право `read:packages`.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|-----------|--------------|------------|
| `BASE_PATH` | `/travel` | базовый путь; на этапе сборки вшивается в бандл |
| `DATABASE_URL` | локальная база | строка подключения к PostgreSQL |
| `PUBLIC_ORIGIN` | `http://127.0.0.1:4173` | origin для ссылок-приглашений, когда в запросе нет заголовка `Origin` |
| `UPLOAD_DIR` | `./data/uploads` | каталог вложений; в образе `/app/data/uploads` |
| `SPA_DIST_DIR` | рядом с кодом | каталог собранного SPA; без него приложение работает как чистый API |
| `TRAVEL_SKIP_MIGRATIONS` | `false` | аварийно поднять сервер, не применяя миграции |
| `MAX_UPLOAD_BYTES` | 15 МБ | предел размера одного вложения |
| `MAX_IMPORT_BYTES` | 200 МБ | предел размера файла импорта |
| `SESSION_TTL_DAYS` | 30 | срок жизни сессии |

### Миграции

Контейнер применяет миграции сам, при старте, до открытия порта, под
advisory-блокировкой PostgreSQL: при одновременном старте нескольких экземпляров
файлы накатит ровно один, остальные дождутся его. Отдельный шаг развёртывания не
нужен.

Локально то же самое запускается вручную:

```bash
pnpm db:migrate
```
